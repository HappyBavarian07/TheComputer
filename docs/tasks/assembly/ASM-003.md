# ASM-003 — Fix assembler / decoder / spec correctness bugs found while validating the assembly guide

## Description

A batch of verified defects and spec/code mismatches found by actually assembling and running programs while writing docs/ASSEMBLY_GUIDE.md. Every item below was reproduced against this branch's compiled code (not inferred from reading). The CALL/RET bugs from the same investigation are already fixed (90bf884, see docs/reviews/2026-09-28-cpu-call-ret-bug.md) and are not part of this ticket. Workflow: align on the design decisions first (see Notes), Developer implements, Team Lead reviews.

## Acceptance Criteria

1. B1: decode and decodeNullable never throw ArithmeticException (or any narrowing error) for any 64-bit word. decode may still throw IllegalInstructionException / IllegalConditionException for unknown opcode or condition fields; decodeNullable returns nulls instead. Disassembler.disassemble(0x80000000L) and the GUI disassembly panel work on arbitrary memory.
2. B2/B3: negative immediates are writable in source and execute with the agreed extension semantics per instruction; assemble -> disassemble -> assemble round-trips negative immediates.
3. B4: using pc/sp/ir/flags as an instruction operand produces a clean diagnostic (or is supported), never a NullPointerException.
4. B5: directive alignment is enforced in one place with one rule, at resolve time, with a clear message; AssemblerCli output matches the GUI export byte-for-byte for programs with unaligned directive data.
5. B6: docs/ISA_SPECIFICATION.md and OpCode.java agree on HALT's opcode and STORER's operand roles (whichever side is chosen as correct).
6. B7/B8: DIV/MOD flag behavior and stack over/underflow exception naming implemented as decided below.
7. B10/B11: DIV/MOD are signed (truncate toward zero, remainder takes the dividend's sign); MUL's V flag means signed overflow; documented and tested.
8. B12: division by zero is a defined fault that halts the CPU with a recorded reason, never an uncaught exception that leaves the CPU running.
9. Target program: a recursive multiply written by the Developer in assembly (using `call`/`ret`, the stack and signed operands) assembles, runs and gives the right answer for the test matrix in Notes, and leaves SP where it started.
10. Regression tests exist for every fixed item; all bundled examples in src/main/resources/programs still assemble and run; docs/ASSEMBLY_GUIDE.md section 9 updated to match.

## Notes

Reproductions live in docs/ASSEMBLY_GUIDE.md section 9. The GUI's Save bin (WorkbenchController.assembleToBinary) already writes correct bytes for B5 and has tests; it is the reference for what AssemblerCli should produce.

### Alignment decisions (2026-09-28)

Decided with the Developer (branch: ticket/ASM-003-assembler-decoder-fixes):

- D1, immediate kinds (per opcode, one table on OpCode shared by encoder, decoder and disassembler):
  - SIGNED32: MOVI, ADDI, SUBI, CMPI, and the LOADR/STORER offset. Range -2^31..2^31-1, sign-extended to 64 bits.
  - UNSIGNED32: ANDI, ORI, XORI. Range 0..2^32-1, zero-extended.
  - SHIFT: 0..63.
  - ADDRESS (jumps, CALL, LOAD/STORE absolute): unsigned 0..2^32-1.
  - Consequence: `movi r1, 0xFFFFFFFF` becomes an error (it is out of SIGNED32 range). Large constants are built with movi + shli + ori.
  - The lexer/parser gains a unary minus for immediates.
- D2, DIV/MOD become signed: quotient truncates toward zero (Java/C semantics), remainder takes the sign of the dividend, MIN / -1 = MIN with V set.
- D3, special registers: `sp` is readable and writable in MOV/ADDI/SUBI. `pc`, `ir`, `flags` are rejected with a clear diagnostic (never an NPE). r29-r31 are plain GPRs; the ABI row "R29 = SP" in LANGUAGE_SPECIFICATION section 6 is corrected.
- D4, STORER: keep the code (RAM[rs1 + offset] = rd, same role order as LOADR), fix the spec text.

Confirmed by the Developer (alignment closed):

- D5: DIV/MOD clear C and V like the logic ops; MUL's V flag is signed overflow.
- D6: zero divisor is a defined fault: CPU halts, reason recorded and shown by the GUI (exception type is a Developer choice, but it must not escape step() leaving the CPU in RUNNING).
- D7: data directives (.byte/.word/.ascii) are byte-precise, with no alignment requirement; instructions must start 8-byte aligned (error otherwise); add `.align N`.
- D8: one shared assembler facade returns a byte image; AssemblerCli and the GUI both use it. AssemblerCli gets a real main(). GUI assembleToBinary becomes a thin delegate to the facade (Team Lead does that part, GUI carve-out).
- D9: split StackUnderflowException from StackOverflowException.

### Additional findings (reproduced)

- B10 (HIGH, cpu): DIV and MOD are unsigned only. -7 / 2 = 9223372036854775804 and -7 % 2 = 1. Any program using signed division (including the recursive multiply's parity or sign tricks) is wrong today.
- B11 (MEDIUM, cpu): MUL's V flag is unsigned overflow. -7 * 2 = -14 (correct value) but V = 1.
- B12 (MEDIUM, cpu): a zero divisor throws ZeroDivisionException out of Cpu.step and the CPU is not halted.
- B13 (MEDIUM, spec): LANGUAGE_SPECIFICATION section 6 disagrees with the machine: R29 is a plain GPR, not SP (SP is a special register, reachable only through D3); R0 is not hardwired to zero; the return address is at [FP+8], not [FP+16] (PUSH/POP and CALL are 8 bytes); a prologue like `mov fp, sp` needs the sp operand from D3. Spec text is fixed in the same change as D3.

### Target program: recursive multiply

The Developer writes it (Team Lead does not supply a solution). It is the end-to-end proof for this ticket: negative literals (B2), signed compare with the N flag (condition codes), sp/functions (B4/D3, call/ret) and the stack all have to work together.

- Contract: multiply(m, n) -> m * n without MUL, recursive, n may be negative or zero. Suggested calling convention: m in r1, n in r2, result in r3.
- Layout: main first (entry point is address 0), `halt`, then the function below it.
- Test matrix (result in r3, SP equals its initial value at halt): 7*5=35, 6*(-4)=-24, 0*9=0, 9*0=0, (-3)*(-3)=9 if the program handles a negative m, 1*1=1.
- Stack discipline check: a recursion depth of 100 (n=100) must not corrupt memory and SP must return to STACK_BASE_ADDRESS.
- Extra: a variant using `div`/`mod` by a register holding 2 (Russian-peasant style) once D2 lands, to exercise signed DIV/MOD.

Verification matrix from alignment:

- Boundary words 0x7FFFFFFF / 0x80000000 / 0xFFFFFFFF through decode, disassemble and execute.
- assemble -> disassemble -> assemble round-trip per immediate kind.
- -7/2 = -3, -7%2 = -1, 7/-2 = -3, 7%-2 = 1, MIN/-1 = MIN with V set, x/0 = fault.
- `.org 0x100 / .word A / .word B / halt` gives identical bytes from AssemblerCli and the GUI export.
- All five bundled examples produce unchanged results.

## Blueprint

### Goal

Make the assembler, instruction decoder, disassembler and ISA spec agree with each other and with the running CPU, so that what the assembler accepts is exactly what the CPU can decode and execute, and no input crashes a tool.

### In Scope

- B1 (HIGH, decoder): InstructionDecoder.decode and decodeNullable use Math.toIntExact(wordValue & 0xFFFFFFFFL) and throw ArithmeticException for any imm32 >= 2^31. Repro: Disassembler.disassemble(0x0000000080000000L) throws; hand-encoding addi r1, r1, 0xFFFFFFFF crashes Cpu.step. Also violates DIS-001's never-crash-on-arbitrary-bytes requirement.
- B2 (HIGH, assembler): no negative literals - IndexedLexer rejects '-' (unexpected character), and InstructionWordEncoder.imm() only accepts 0..MEMORY_SIZE_BYTES-1 (about 28 bits, positive only) with a stale 'imm16' in its error text.
- B3 (MEDIUM, cpu/spec): immediate extension semantics undefined in practice - spec says sign-extend for ADDI/SUBI and zero-extend for ANDI/ORI/XORI, code sign-extends all via int. Cannot be tested until B1 is fixed.
- B4 (MEDIUM, assembler): pc/sp/ir/flags lex as REGISTER tokens and parse as operands, but SymbolResolver.resolveOperand returns a null value for them, so InstructionWordEncoder.reg() throws NullPointerException. Repro: mov r1, pc.
- B5 (MEDIUM, assembler): directive alignment is inconsistent - SymbolResolver only checks .word, DirectiveDataEmitter requires every .word/.byte/.ascii to start 4-byte aligned and fails at encode time; and AssemblerCli.writeBinary steps in 8-byte strides, so with '.org 0x100 / .word A / .word B / halt' it silently writes zeros for the second .word and the halt (the GUI export writes them correctly).
- B6 (MEDIUM, spec drift): ISA_SPECIFICATION.md lists HALT as 0x05 but OpCode.HALT is 0x03; the STORER formula is written RAM[Rd+imm]=Rs1 but the code does RAM[Rs1+offset]=Rd.
- B7 (LOW, cpu): DIV and MOD never touch C/V (they keep stale values) while AND/OR/XOR/NOT/shifts clear them; division-by-zero behavior not yet characterized.
- B8 (LOW, cpu): StackOverflowException is thrown for both push-past-limit and pop-from-empty; the second is an underflow.
- B10-B13: see Additional findings in Notes (signed DIV/MOD, MUL V flag, zero-divisor fault, LANGUAGE_SPECIFICATION section 6 ABI mismatches).
- B9 (LOW, tooling): AssemblerCli has no main() and pom.xml configures no runnable entry point, so there is no command-line assembler today; the GUI no longer uses it.

### Out of Scope

- CALL/RET (already fixed in 90bf884).
- Language/compiler work (LANG-001 and downstream), GUI features, label reconstruction in the disassembler.
- New instructions or condition codes.

### Topology

isa (OpCode, Condition, InstructionDecoder) <- assembler (lexer, parser, resolver, encoder) and disassembler <- gui. The decoder and the encoder must stay mirror images: any change to immediate range or extension is made in both, plus the spec and the disassembler, in the same change.

### Steps

- Alignment done: decisions D1-D9 recorded in Notes; follow Milestones M1-M7 in that order.
- B1 + B3: fix decoder immediate handling and define per-instruction extension; add decoder and disassembler tests over boundary words (0x7FFFFFFF, 0x80000000, 0xFFFFFFFF).
- B2: add unary minus to the lexer/parser, update the encoder range check and its error text; round-trip test with negative immediates.
- B4: reject special-register operands with a proper diagnostic (or implement them).
- B5: move alignment checks to resolve time with one rule; make AssemblerCli and the shared pipeline emit identical bytes.
- B6: reconcile ISA_SPECIFICATION.md and OpCode/Cpu for HALT and STORER.
- B7/B8/B9/B10/B11/B12: apply the agreed decisions and document them.
- B13: correct LANGUAGE_SPECIFICATION section 6 (ABI table, frame offsets).
- Developer writes the recursive multiply (target program) and runs the test matrix as the final end-to-end check.
- Update docs/ASSEMBLY_GUIDE.md section 9 and the GUI's OpcodeReference notes to match; delete notes for anything fixed.

### Hazards

- Encode/decode drift is the core risk: assembler range check, decoder, disassembler and spec must change together.
- Zero-extend versus sign-extend per instruction is easy to get wrong silently, especially for ANDI/ORI/XORI masks with the top bit set.
- Math.toIntExact-style narrowing elsewhere may hide the same bug; grep for it when fixing B1.
- Bundled examples and the GUI must keep working: run every program in src/main/resources/programs after each step.
- The GUI disassembly panel feeds arbitrary memory words into the decoder, so decoder regressions show up there first.
