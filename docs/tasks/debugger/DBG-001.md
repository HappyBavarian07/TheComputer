# DBG-001 — Implement Debugger (step, breakpoints, views)

## Description

Provide step execution, breakpoints, register/memory/stack views, and basic watch expressions.

## Acceptance Criteria

1. Step through instructions and inspect registers & memory.
2. Set/clear breakpoints.
3. Present human-readable assembly alongside machine code.

## Notes

Essential for development productivity. Formalizes the ad-hoc step/run/watch logic currently living in the vibecoded GUI workbench into a real module the GUI can consume.

## Blueprint

### Goal

A headless debugger core that drives the existing CPU/Motherboard through controlled execution (single-step, run-to-halt, run-to-breakpoint) and exposes read-only inspection of registers, flags, memory, and the stack — with no debug logic living in the GUI.

### In Scope

- Debugger controller wrapping Motherboard/Cpu lifecycle (attach, step, run, pause, reset).
- Breakpoint set keyed by instruction address; execution halts before executing a break address.
- Read-only inspection snapshots: register file, PC/SP/IR, ALU flags (Z/N/C/V), memory window, stack window.
- Watch expressions over registers and absolute addresses (the GUI Watch panel already models this).
- Human-readable disassembly of the current instruction (delegate to DIS-001 when available; interim: local decode).

### Out of Scope

- GUI wiring (separate; GUI consumes this module).
- Source-level / symbolic debugging (needs debug info from the compiler chain).
- Reverse execution, conditional breakpoints, data watchpoints (future).
- MMU/permission traps (owned by MEM-002).

### Topology

gui -> debugger -> cpu -> memory -> isa. Debugger sits above the CPU cycle, observing via existing read APIs; it must never mutate architectural state except through the CPU's own step entrypoint. Layer isolation preserved (one-way deps).

### Steps

- Define a Debugger controller interface: attach(Motherboard), step(), run(maxSteps), addBreakpoint(addr), removeBreakpoint(addr), state().
- Introduce an immutable inspection snapshot type (registers, special regs, flags, decoded current instruction) built from existing getters — no new aliasing of Bit objects.
- Implement the run loop as repeated single-steps guarded by a breakpoint check on PC before each fetch; stop on HALT, breakpoint hit, or step budget.
- Add watch-expression evaluation: parse the same targets the GUI accepts (rN, sp, pc, 0xADDR) and resolve against the snapshot.
- Wire disassembly of the current instruction; keep a seam so DIS-001 can replace the interim decoder.
- Cover with unit tests: breakpoint halts before the target executes, step advances exactly one instruction, snapshots reflect post-step state.

### Hazards

- Bit ownership: snapshots must deep-copy values, never share Bit objects with the live register file/memory.
- Zero-allocation contract in the hot path stays in core/cpu — the debugger observes, it does not run inside the ALU/adder inner loops.
- Breakpoint semantics: halt BEFORE executing the break address (pre-fetch), not after, or stepping past a breakpoint becomes ambiguous.
- Run budget to avoid infinite loops on programs without HALT.
